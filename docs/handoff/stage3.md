# Задача: этап 3 без внешних сервисов и отложенные функции этапов 1–2

**Начинай от ветки `claude/core-flow-real-companies-vybdfs`, а не от `main`.** В ней
регистрация по настоящему БИН, SMS Mobizon и флаг `hide_demo_companies`; её вливают в `main`
отдельно. Свою ветку назови `feature/stage3`.

Ключей, договоров и внешних вызовов нет. Всё, что требует внешнего сервиса, не делай:
ИС ЭСФ и ИС МПТ, 1С по API, iiko / r_keeper / Poster, банки, карты, нативное приложение.

Где ТЗ не задаёт правило, выбери простое значение по умолчанию, вынеси его в настройки
платформы (`PlatformSetting`) и пометь `TODO(open-question)`. Каждое такое решение перечисли
в отчёте.

## A. Отложенные функции этапов 1–2

1. **Голосовые сообщения в чате (3.7).** Запись в браузере через MediaRecorder без новых
   зависимостей. Аудио хранится как вложение (`Attachment` + `AttachmentBlob`,
   `src/lib/files/attachments.ts`): добавь распознавание webm/ogg/mp4 по первым байтам.
   Ограничения: длина до 2 минут, размер в пределах текущего лимита. В переписке —
   плеер `<audio>`.
2. **Чат в реальном времени (3.7, 5.3).** Server-Sent Events через route handler, без новых
   зависимостей и без Redis. Сервер опрашивает базу раз в 2 секунды, только по чатам
   своей компании (правило 4). Если поток оборвался, клиент переподключается, а пока его
   нет, обновляет переписку прежним запросом.
3. **Объединение дублей товаров (3.13).** В админке Суперадмин или Контент-менеджер выбирает
   главный товар и дубль. Все ссылки переносятся одной транзакцией: `SupplierOffer`,
   `StockBalance`, `StockMovement`, `StockBatch`, `StockDocumentLine`, `RetailPrice`,
   `ReceiptItem`. Дубль удаляется, действие пишется в журнал админки.
   Если перенос нарушит уникальность (у одного поставщика есть оба товара, у одной точки
   оба остатка, у одной компании обе цены), не сливай: покажи, что именно мешает.
   Справочник брендов — по полю `Product.brand`: список с количеством товаров и
   переименование бренда.
4. **Продажа поштучно из упаковки (4.1, 4.2).** Магазин задаёт у своей розничной цены
   число штук в упаковке и цену штуки (`RetailPrice` — не таблица D1, её можно расширить).
   Касса продаёт штуки. Остаток уменьшается на долю упаковки до 3 знаков (правило 2),
   округление — `TODO(open-question)`. В чеке видно, что продажа поштучная.
   Не сломай маркированный товар: его поштучно не продают.
5. **Баннеры в кабинете (3.13).** Администратор создаёт баннер: текст на русском и
   казахском, для кого (все, магазины, поставщики), даты показа. В кабинете баннер можно
   закрыть, закрытие запоминается в браузере.

## B. Этап 3 ТЗ

6. **Программа лояльности на кассе.** Бонусы по номеру телефона покупателя: на кассе вводят
   телефон, чек начисляет процент бонусами, следующей покупкой можно списать до
   какой-то доли чека. Процент и доля — настройки платформы. Начисление и списание —
   движения бонусного счёта в транзакции чека, по образцу правила 3 для остатков.
   Списание уменьшает сумму к оплате и отражается в чеке, на фискализации и в Z-отчёте.
   Возврат чека откатывает и начисление, и списание. Телефон покупателя в логи — только
   маской (правило 11). У каждой компании свои покупатели.
7. **Аналитика (магазин и поставщик).** Экран «Аналитика»:
   - у магазина — продажи и валовая прибыль по дням и категориям, ABC-анализ товаров,
     оборачиваемость и залежавшийся товар;
   - у поставщика — оборот по магазинам и товарам, доля выполненных заявок, топ магазинов.
   Выгрузка в Excel. Графики — SVG своим кодом, без библиотек. Рекомендации закупок уже
   есть в `src/lib/stock/replenishment.ts`, их переиспользуй, а не переписывай.
8. **Торговые представители (поставщик).** Новая системная роль сотрудника поставщика —
   «Торговый представитель» (матрица прав в БД, правило 5). Владелец закрепляет за ним
   магазины, которые уже у него заказывали. Представитель видит только свои магазины:
   историю их заказов у своего поставщика, долги и отметки визитов с комментарием.
   Создавать заказ от имени магазина он не может — это `TODO(open-question)`, нужна
   договорённость о согласии магазина.
9. **Маршруты водителей.** На экране доставок `/deliveries` поставщик собирает рейс на день
   из заявок к отгрузке, задаёт порядок точек вручную и назначает водителя-сотрудника.
   Водитель видит свой рейс по порядку. Печатный маршрутный лист в PDF — через тот же
   рендер, что у документов. Карты и автопостроения маршрута нет: это внешний провайдер.

## Как работать

- **Коммитов мало: один на блок A и по одному на каждый пункт B — не больше 6 всего.**
  Пользователю важна аккуратная история на GitHub.
- Модель D1 (`User`, `Company`, `Location`, `DeliveryZone` и другие из CLAUDE.md) не меняй.
  Новые таблицы и поля в остальных — можно. Миграции создавай через `prisma migrate diff`.
- Тексты — только в `messages/ru.json` и `messages/kk.json`, оба языка полностью.
- Каждый новый маршрут проверяет права (`requirePermission`, `requireAdmin`) и
  принадлежность компании.
- Тесты для каждого пункта:
  - интеграционный — логика и изоляция компаний;
  - e2e на 375 и 1280 px — для лояльности, объединения дублей, представителя и рейса.
  - Новые таблицы добавь в `resetTransactionalData` (`tests/helpers/test-db.ts`)
    в правильном порядке внешних ключей.
- Демо-данные: дополни `npm run db:seed:demo` — бонусный покупатель, баннер, представитель
  с магазинами, рейс водителя. Дополни шаг показа в docs/DEMO.md.
- Обнови CLAUDE.md (раздел этапа 3), docs/REMAINING.md и docs/TZ-demo.md (раздел 8 —
  новые открытые вопросы).
- Перед отчётом всё должно быть зелёным:
  `npm run typecheck`, `npm run lint`, `npm test`, `npm run test:e2e`, `npm run build`.
  `npm test` и e2e запускай по очереди, у них общая тестовая база.
- В `main` не пушь. Запушь `feature/stage3` и опиши в отчёте:
  - что сделано по пунктам;
  - какие миграции накатывать на Railway;
  - решения по умолчанию с `TODO(open-question)`;
  - что не получилось и почему.
