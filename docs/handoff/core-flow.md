# Задача: основной путь работает для настоящих компаний

Заказчик хочет запустить пилот. Сейчас важно одно, остальное не трогай:

1. Поставщик регистрируется по своему настоящему БИН.
2. Поставщик загружает свои товары: из Excel-шаблона или вручную.
3. Магазин регистрируется по своему настоящему БИН.
4. Магазин видит товары поставщиков, которые возят в его город, в ленте и списком.
5. Магазин кладёт товары в корзину.

Демо работает только с тестовыми данными. Твоя задача — пройти этот путь глазами
нового пользователя и убрать всё, что мешает настоящей компании.

## Что уже известно

- `registerCompany` (`src/lib/registration/register-company.ts`) ищет БИН в мок-реестре
  `src/mocks/bin-registry.ts`. Для настоящего БИН он возвращает `bin_not_found`,
  и настоящая компания зарегистрироваться не может. Исправь так:
  - БИН проверяется по контрольной сумме (`isValidBin`), как сейчас.
  - Если БИН есть в мок-реестре, название и адрес подставляются, как сейчас.
  - Если БИН в реестре нет, пользователь сам вводит название компании и юридический адрес.
    Компания создаётся, а пометку «данные не из реестра» видит администратор при проверке
    компании.
  - Подключение настоящего реестра — открытый вопрос заказчика. Пометь его
    `TODO(open-question)`, сам реестр не подключай.
- Флаг `auto_verify_companies` в демо включён, и компании подтверждаются сразу. Не меняй его.
- Код входа из SMS сейчас показывается на экране (`src/mocks/sms.ts`, `/api/auth/request-code`
  отдаёт код в ответе). С живыми людьми так нельзя: любой войдёт под чужим номером.
  Сделай настоящий адаптер SMS-провайдера РК по тому же правилу, что и остальные моки
  (CLAUDE.md, раздел «Моки»): интерфейс тот же, включается переменной окружения.
  - Провайдер — Mobizon (mobizon.kz, HTTP API `message/sendSmsMessage`). Ключ — `SMS_API_KEY`,
    отправитель — `SMS_SENDER`. Если заказчик выберет другого провайдера, адаптер легко
    заменить: пометь это `TODO(open-question)`.
  - Без ключа всё работает как сейчас: мок, код на экране. С ключом код уходит по SMS,
    а в ответе API и на экране его нет.
  - Ошибка провайдера — понятное сообщение пользователю, в логе номер только маской
    (правило 11).
  - Тест: с ключом код не возвращается в ответе, а вызов провайдера мокается в тесте.
  - Добавь `SMS_API_KEY` и `SMS_SENDER` в `.env.example` и README.
- Демо-данные (`npm run db:seed:demo`) — тестовые компании с пометкой «(тест)». Настоящие
  магазины не должны видеть их в ленте. Добавь флаг платформы `hide_demo_companies`
  (`PlatformSetting`, как `auto_verify_companies`). Когда флаг включён, компании из мок-реестра
  `src/mocks/bin-registry.ts` не попадают в ленту, поиск и на карту поставщиков. Флаг
  переключается в админке. По умолчанию он выключен, чтобы демо-сценарий и e2e работали
  как раньше.

## Что проверить и починить

Пройди путь в браузере (Playwright, 375 px и 1280 px) на чистой базе:
новый поставщик → каталог → новый магазин в его городе → лента → корзина.
Чини всё, что ломается или непонятно новому пользователю, в частности:
- онбординг поставщика: города доставки, минимальная сумма заказа, дни доставки;
- скачивание шаблона Excel и загрузку каталога с ошибками в строках:
  понятно ли, что исправить;
- ручное добавление товара по штрихкоду;
- магазин в городе, куда никто не возит: пустая лента должна объяснять, почему она пустая;
- корзину: кратность упаковки, минимальная сумма, разбивку по поставщикам.

Не добавляй функций сверх этого пути. Дизайн можно править через общие компоненты.

## Как работать

- Ветка `feature/core-flow` от `main`.
- **Коммитов как можно меньше: один-три на всю задачу.** Пользователю важна аккуратная
  история на GitHub.
- Тексты интерфейса — только в `messages/ru.json` и `messages/kk.json`, оба языка.
- Если меняется схема, создай миграцию. `npm run db:migrate` требует TTY, поэтому её можно
  создать через `prisma migrate diff`. Таблицы модели D1 (`Company`, `Location` и другие из
  CLAUDE.md) зафиксированы: поле «данные не из реестра» лучше хранить вне `Company`,
  например в `VerificationRequest`. Если без изменения `Company` никак, остановись и напиши,
  почему.
- Тесты:
  - интеграционный — регистрация с БИН вне реестра: валидный БИН проходит, невалидный нет,
    дубль БИН по-прежнему создаёт запрос на доступ;
  - e2e — весь путь от регистрации поставщика до корзины магазина.
- Перед отчётом всё должно быть зелёным:
  `npm run typecheck`, `npm run lint`, `npm test`, `npm run test:e2e`, `npm run build`.
  `npm test` и e2e запускай по очереди, не одновременно: у них общая тестовая база.
- В `main` не пушь. Запушь ветку и опиши в отчёте:
  - что поменялось;
  - нужна ли миграция на Railway;
  - что осталось за заказчиком: SMS-провайдер, реестр БИН, хостинг в РК.
