# B2B-платформа для поставщиков и магазинов (Казахстан) — демо

Источник истины: [docs/TZ.md](docs/TZ.md) — полное ТЗ продукта на три этапа.
Рабочий документ по объёму демо: [docs/TZ-demo.md](docs/TZ-demo.md) — срез ТЗ под демо,
с разделом 4.2 (поля карточки товара), 7 (критерии приёмки) и 8 (открытые вопросы).
При расхождении приоритет у полного ТЗ, расхождение выносится заказчику.

## Стек (зафиксирован, не менять без согласования)

Next.js 16 (App Router) · React 19 · TypeScript 5.9 strict · Tailwind 4 · shadcn/ui ·
PostgreSQL + Prisma 7 · Vitest · Playwright · HTML→PDF через Playwright · ExcelJS ·
next-intl (ru/kk). Новые зависимости — только с объяснением в коммите.

## Правила (нарушать нельзя)

1. Деньги — только Decimal (Prisma Decimal / decimal.js), никогда float. Суммы до 2 знаков.
2. Количества — до 3 знаков (весовой товар).
3. Остатки меняются только через документы движения в транзакции. Прямое редактирование запрещено.
4. Каждый запрос к данным компании проверяет принадлежность пользователя компании. На это есть тест.
5. Ставки НДС, перечни документов, тарифы — в справочниках БД, не в коде. Текущая ставка — 16%.
6. Все тексты интерфейса — в `messages/ru.json` и `messages/kk.json`. Строк в коде нет.
7. Не реализовывать то, что не входит в демо. Сомнение — остановиться и спросить.
8. Не добавлять фичи сверх ТЗ и не «улучшать» дизайн сверх описанного.
9. Открытые вопросы ТЗ не решать самостоятельно — помечать `TODO(open-question)`.
10. Создание документов и приёмка защищены от двойного нажатия (idempotency key).
11. В логах не писать телефоны и ИИН/БИН целиком.
12. Данные демо — только тестовые. Реальных данных компаний в коде нет.

## Моки (интерфейс как у реальных сервисов)

- SMS: код входа показывается в интерфейсе, реальной отправки нет.
- Реестр БИН: мок-справочник тестовых компаний, подтягивает название и адрес.
- Уведомления (WhatsApp/Telegram/email): мок-адаптер, пишет в лог и в интерфейс.

Реальных ключей и внешних вызовов в демо нет.

## Что в демо не входит

Склад (кроме прихода по накладной), касса POS, онлайн-оплата, ЭЦП, ЭСФ, маркировка, онлайн-касса,
интеграции с 1С и iiko. Чат — статичный макет без логики.
Сотрудники с матрицей прав (3.12), админ-панель (3.13) и рейтинги (3.8) реализованы после D7.

## Этапы

D0 каркас · D1 регистрация · D2 каталог поставщика · D3 выбор товаров магазином ·
D4 заявки · D5 накладная и приёмка · D6 оплата и макеты · D7 приёмка демо.

Порядок работы: план → подтверждение заказчика (если есть серые зоны) → реализация небольшими
коммитами в ветку `feature/{этап}` → typecheck, lint, тесты зелёные → отчёт → ожидание проверки.

## Команды

```
npm run dev          # http://localhost:3000 → /ru
npm run typecheck    # tsc --noEmit
npm run lint         # eslint
npm test             # vitest (логика)
npm run test:e2e     # playwright (375 px и 1280 px)
npm run build
npx prisma generate  # обязательно после клонирования: src/generated в .gitignore
npm run db:migrate   # только prisma migrate dev; при предупреждениях нужен TTY (expect)
npm run db:seed
npm run db:seed:demo # демо-данные для показа: компании, каталоги, заявки
```

Локальная БД: PostgreSQL 18 через Homebrew, `brew services start postgresql@18`,
базы `b2b_demo` (разработка) и `b2b_demo_test` (автотесты).

`npm test` и `npm run test:e2e` используют одну тестовую базу, поэтому запускать их
одновременно нельзя: прогоны затрут данные друг друга. Сначала один, потом второй.

## Решения, принятые с заказчиком

- Оба языка (ru и kk) заполняются полностью с самого начала, включая PDF документов.
- Города: справочник всех областей и областных центров РК; демо-данные — Алматы и Тараз
  (критерий приёмки ТЗ про Тараз).
- База: разработка на локальном PostgreSQL, боевая — Railway. Для переезда меняется только
  `DATABASE_URL`. Автотесты всегда идут в отдельную базу из `TEST_DATABASE_URL`.
- Модель данных зафиксирована в D1: `User`, `OtpCode`, `Session`, `Company`, `Membership`,
  `Location`, `DeliveryZone`, `CompanyAccessRequest`, `Region`, `City`, `VatRate`. Следующие
  этапы только добавляют таблицы; изменение этих — серая зона, требует согласования.
- D2 добавил таблицы каталога: `Unit`, `Category`, `Product`, `SupplierOffer`.
- Рейтинги добавили `Rating`: оценка по закрытой заявке, одна от каждой стороны,
  автоматические метрики считаются по заявкам за 12 месяцев.
- Админ-панель добавила `AdminUser`, `AdminSession`, `VerificationRequest`, `AdminAuditLog`,
  `ImpersonationLog`, `PlatformSetting`. Флаг `auto_verify_companies` в демо включён:
  компании подтверждаются автоматически, иначе показ упирается в модерацию.
- Сотрудники и права добавили `Role`, `Permission`, `Invitation`, `AuditLog` и поля
  `roleId`, `allowedLocationIds`, `orderLimit`, `maxDiscount` у `Membership`.
  Матрица прав живёт в справочнике БД (правило 5), доступ к API — через `requirePermission`.
- D6 добавил `Payment` и реквизиты компании (ИИК, БИК, банк) с проверкой IBAN.
- D5 добавил `Document`, `StockMovement`, `StockBalance` и поля приёмки у `OrderItem`.
- D4 добавил `NumberSequence`, `IdempotencyKey`, `Notification`, `OrderStatusLog`.
  Номер заявки уникален в пределах магазина, а не глобально (раздел 3.5 ТЗ).
- D3 добавил `SwipeAction`, `Cart`, `CartItem`, `Order`, `OrderItem`. `Order` заведён заранее:
  кнопка «Повторить прошлый заказ» из D3 читает прошлую заявку. Переходы статусов — в D4.
- Мок-реестр БИН: 12 именованных компаний для показа и пул из 400 сгенерированных для автотестов.
- Юрмодель для демо — «доска объявлений»: документы между магазином и поставщиком,
  платформа в расчётах не участвует (раздел 2 ТЗ, открытый вопрос).
- Хостинг Railway не соответствует закону РК №94-V о локализации персональных данных.
  Для пилота с реальными магазинами нужен дата-центр в РК.
